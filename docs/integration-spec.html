What it is

A spec builder, not a form

Today every custom-product collection page links to one HubSpot form whose main field is custom_quote_message — free text, described in your portal as "a customer to give description of what they are looking to purchase." A rep reads prose and phones back to ask what was meant.

The builder replaces that with five screens that produce a structured request. The customer picks products, sizes and quantities; the rep receives a spec they can price without a discovery call.

  1. 01BuildCategory pills, product cards, and a configurator for size and quantity. A running list on the right collects what they pick.
  2. 02ReviewEvery line grouped by category, quantities adjustable a case at a time, anything removable with an undo.
  3. 03DetailsFour chip questions — deadline, artwork, use, one-off or repeat — plus a free-text box for anything the catalogue can't express.
  4. 04ContactName, business, email, phone. Deliberately last: the work is already done and saved, so the ask is earned.
  5. 05ConfirmationWhat was sent, the address it went to, a reference number, and the four steps that follow.

Two rules that shape everything

Quantities on a line are alternatives, never a sum. Picking 5,000 and 10,000 means "price both", not "I want 15,000". This is why there is no grand total anywhere — adding cups to sleeves to jars produced a number nobody could use, sitting exactly where a checkout puts the money.

Nothing is a purchase. No cart language, no prices, no payment. The vocabulary is "quote request" throughout, and the reassurance is repeated on every screen that asks for something.

The mechanism

Three systems, two boundaries

The whole integration is a question of what crosses each boundary and when. Everything between the two crossings is the prototype you already have.

Data shapes

Three objects hold everything

These are the real shapes in the prototype. Getting them right in Shopify is most of the migration.

ShopifyA product

Six of these drive the whole catalogue: the cards, the configurator, the review maths and the deadline check.

{ id: "sw", group: "Coffee Cups", name: "Single Wall Paper Cup",
  unit: "cups", blurb: "Standard hot cup. Needs a sleeve for hot drinks.",
  moq: 5000, per: 1000, lead: "3–4 weeks", leadMax: 4,
  note: "Standard 90mm rim, the common size…",
  lid: "Also quote matching 90mm lids",
  sizes: [["8 oz"], ["12 oz"], ["16 oz"], ["20 oz"]],
  tiers: [5000, 10000, 25000, 50000] }

per is the case size, so quantities only move a whole case at a time. leadMax is the numeric weeks used to warn when a deadline is too tight — with jars at 4–6 weeks, answering "2–3 weeks" fires a clash notice naming the slowest product on the request.

BrowserA quote line

One per product-and-size the customer adds. qtys is an array because a line can carry alternatives.

{ pid: "sw", name: "Single Wall Paper Cup", size: "12 oz",
  qtys: [5000, 10000],   // "price both", not 15,000
  per: 1000, cold: 0, unsure: false }

unsure: true is the "Not sure yet" path — it stages the line at the minimum and flags it for the rep as help me size this, so an unknown quantity stops being a dead end.

BrowserThe session

Written to localStorage on every change and restored on load. This is what makes asking for an email at screen four defensible rather than reckless: the work is not hostage to the contact details.

{ quote: [ …lines… ],
  answers: { when, artwork, use, cadence },
  note: "Also need napkins and a 10oz if you make one.",
  lids: ["sw", "clear"],
  tab, open, screen }

One behaviour worth preserving

Sending is terminal. On submit the session is cleared and a flag stops anything re-saving it, so walking Back off the confirmation cannot resurrect a request that was already sent, and the form cannot fire twice. Four separate reviewers found the version without this.

Connecting it

Four joins

1 · The entry point Shopify

A small section on each custom collection page, in the slot the HubSpot form occupies now. It should name what they get rather than what they do, and state the minimum before the click so a shop that can't do 5,000 finds out here instead of after four screens.

Link it as /pages/custom-quote?category=coffee-cups. The builder opens on that category with all five pills still live — pre-selecting, not locking.

2 · The page Shopify

A page template with the builder as one Canopy section. Not a modal: the five screens already have real URLs, working browser back/forward and restorable state, and a modal loses all three while adding scroll-lock problems on the device most of these customers are using.

3 · The catalogue Shopify

The six-product array becomes product metafields, printed into the page by Liquid as JSON on load. No fetch, no loading state — the builder reads the same shape it reads today.

Sizes come from the product's own variants, and the photograph from its featured image — which also removes the 160 KB of base64 currently inlined in the prototype.

4 · The submit HubSpot

The one crossing. Three layers, because a request is multi-line and contact properties are flat:

ObjectCarriesWhy there
Contactname, email, phone, company, plus the four chip answersPerson-level facts that should persist across requests and feed segmentation
Dealreference number, readable summary, needed-by, and the raw JSON in a hidden propertyWhat the rep actually works — gives it a pipeline, an owner and reporting
Line items
optional, later		one per product and quantityOnly if you want "how many people asked for 16 oz double wall" as a report

Keep the raw JSON regardless. It costs one property, and it means changing how the request is displayed later doesn't lose data you already captured.

The part that needs a decision

A HubSpot Forms API submission can create or update a Contact but cannot create a Deal. Getting a Deal means either a Workflow (Professional and above) or a small server-side call — a Shopify app proxy route, or a function that holds the private-app token. That token must never reach the browser, which is the one genuine piece of backend work in this project.

Order of work

Build it in this order

  1. Catalogue into metafields

    Define the metafield set, populate all six products, confirm the two case sizes that are still assumptions — cups at 1,000 and sleeves at 2,500.

    Blocks everything else. Nothing can be built against a catalogue that doesn't exist yet.

  2. The Canopy section and page

    Scaffold the section, port the markup to Liquid with the theme's classes, and print the catalogue JSON from the metafields. Spacing resolves itself here by inheriting the theme.

    needs 1

  3. The collection-page CTA

    A second, much smaller section replacing the HubSpot form module, linking through with the category parameter.

    needs 2

  4. The submit endpoint

    Contact upsert plus Deal creation, with the raw JSON stored. Build it behind an app proxy so the token stays server-side. Until it exists the builder can post to a plain HubSpot form so the flow is testable end to end.

    independent of 2 and 3 — can run in parallel

  5. Test on real devices

    Every measurement in this project was taken in headless Chromium. The mobile experience in particular deserves a real phone before customers see it.

    needs 2, 3, 4

Unresolved

Open questions

Can you use a custom object?

Your portal has none defined today, and the account API reports accountType: STANDARD — which means a normal production portal, not a subscription tier, so it does not answer the question. A "Custom Quote Request" object would be cleaner than overloading Deals. Check Settings → Objects before committing to the Deal shape.

Are the two case sizes right?

Cups at 1,000 per case and sleeves at 2,500 are inferences, not given facts. Only the jar (147) came from you. These print on the review screen as "5 cases of 1,000", so an error is customer-visible.

Does a Shopify draft order get created too?

Or is HubSpot the only system of record until the deal closes? This changes whether the submit endpoint talks to one API or two.

What are the theme's real spacing values?

The container gutter is settled at 20px from the sizes calc in your Liquid. Vertical rhythm, --space-unit and grid gaps are still the prototype's own choices and should inherit from the theme instead.
